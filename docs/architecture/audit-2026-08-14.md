## 1. Corpus-supply: readiness for a topics artifact

Files: `packages/core/src/corpus-supply/{model,errors,service,source,bible-artifact}.ts`

**Applied (`8ad245b6`):**

- `CorpusName` (`'bible' | 'writings'`) and `CorpusIdentity`
  (`'canonical' | PublicationId`) are now defined once in `model.ts`.
  `CorpusActivation`, `CorpusSupplyReceipt`, `CorpusInstallationError`, and
  `CorpusRecipeUnavailableError` all narrow from them. Adding the topics
  corpus starts with one vocabulary change instead of four scattered literal
  edits. (`CorpusRecipeUnavailableError.corpus` was a bare `NonEmptyString`;
  it is now the same literal set.)
- `CorpusSupply.ensure` previously dispatched with if-chains that fell
  through to `ensureWritings(undefined)` for any unrecognized tag. A fourth
  `CorpusTarget` variant (topics) would have compiled and silently installed
  every writings publication. The dispatch is now an exhaustive `switch` on
  `target._tag`; a new target tag is a compile error at the dispatch site.

**Assessment for the build:** the module is in good shape for a third corpus.
The topics artifact should follow the `bible-artifact.ts` template — a
single-file, digest-declared artifact behind a `TopicsArtifactRecipe` +
`TopicsArtifactInstaller` service pair — not the per-publication writings
path. `Effect.serviceOption` wiring in `CorpusSupply.layer` means hosts that
do not supply topics recipes degrade to `CorpusRecipeUnavailableError`
exactly like bible/writings do today. No further prep is safe to do without
the artifact schema (ticket 001 owns that).

## 2. Procedure group: adding RPC families

Files: `packages/core/src/procedure/{group,handlers,model}.ts`

**Applied (`10ff9cdb`):** all 23 domain procedures now go through one
`procedure(tag, { payload, success, stream? })` constructor that fixes the
failure convention (`ProcedureError` + sanitized defect) structurally.
`RuntimeConnect` remains the single raw `Rpc.make` because it fails with the
handshake error. The study-pane and wiki families add procedures without
repeating the convention.

**Verified map claim:** Strong's, cross-refs, and margin-note queries are
complete in `packages/core/src/bible-db/bible-database.ts`
(`getStrongsEntry`, `searchStrongs`, `getVersesWithStrongs`,
`getChapterStrongs`, `getCrossRefs`, `chapterMarginNotes`, …) with a
`layerTest` factory, and have no procedure in `group.ts` and no consumer in
`packages/app`. Commentary lives in `packages/core/src/egw-commentary/`
(CLI-only today). These are the ready-made backends for the
`v1.study.*` family.

**Left alone:** `handlers.ts` repeats the procedure tag string inside
`normalizeFailure('v1…')` per handler. Copy-paste drift risk is real but
small; restructuring the handler map to derive the label from the key is not
worth the type gymnastics now.

## 3. bible-rendering segments: phrase-link extensibility

Files: `packages/core/src/bible-rendering/{segments,margin-notes}.ts`

The segmentation pipeline (`TextSegment` union + ordered `apply*` passes) is
the right shape for the phrase-dictionary layer: a wiki link becomes one new
segment variant plus one pass, exactly like search highlighting. Margin-note
anchoring in `segmentVerseText` is the pattern phrase matching will follow.

**Finding (no change made): the module has zero consumers.**
`packages/app/src/reading/bible-reader.tsx` renders `{verse.text}` raw — the
KJV editorial conventions (leading `¶`, `[bracketed]` italics, `‹…›` red
letters) that `segmentVerseText` handles are currently displayed literally
in the shared app. Adopting `bible-rendering` in `packages/app` is part of
the wiki build's rendering-rules work, not this audit. The module stays.

`packages/core/src/bible-cross-refs/` (classification taxonomy +
`AuthoredCrossRef`) is likewise built, tested, exported, and unconsumed. It
sits on the study-pane cross-refs seam, so it also stays.

## 4. Topics module: overlay base

Files: `packages/core/src/topics/{model,service}.ts`

Clean read-only catalog: branded `TopicId`, `TopicSummary`/`TopicDetail`
schemas, SQL-backed `TopicService.Live` plus an in-memory `TopicService.Test`
factory. The wiki overlay ("matching catalog topics contribute an auto-mined
references section; catalog is the long-tail fallback") composes on top of
this without modification — a wiki `TopicPageService` should wrap or join,
not extend, this service. No changes; nothing blocking.

## 5. Writings / search: hybrid EGW search seam

Files: `packages/core/src/writings/service.ts` (search, lines 354-384),
`packages/core/src/egw-db/book-database.ts` (`searchParagraphs`, lines
855-889), `packages/core/src/bible-db/bible-database.ts`
(`searchVerseWindow`).

Documented, deliberately unchanged (tickets 013/014 own the redesign):

- EGW search is FTS5 lexical only. `searchParagraphs` has **no ORDER BY** —
  results are unranked, unlike Bible search's `ORDER BY rank`.
- The raw user query is passed to `MATCH` unescaped. A malformed FTS5 query
  (unbalanced quote) surfaces as `WritingsUnavailableError` instead of
  `WritingsInvalidSearchError`. Bible search strips `['"*]` first.
- There is **no writings-search procedure** in `group.ts`; only
  `v1.reading.bibleSearch.get` exists. The parity matrix "Search" row is
  currently satisfied by Bible search alone.
- The hybrid engine seam is `EGWParagraphDatabase.searchParagraphs` /
  `WritingsService.search`; both are behind service interfaces, so replacing
  the engine is a layer swap, not a caller migration.

## 8. Legacy cache.sqlite migration paths (documented, not touched)

Files: `apps/desktop/electron/user-state-generation.ts`,
`packages/core/src/local-first/copy-on-migrate.ts` + `legacy/*`,
`packages/core/src/db/schema-version.ts`.

The desktop migration is copy-on-migrate: it snapshots three legacy sources
**read-only** — `cache.sqlite` (positions + row counts), `settings.json`,
and optional CLI state — fingerprints each, derives a deterministic
generation name (`user-state-v1-<hash16>`), projects legacy rows into tagged
domain mutations with deterministic IDs/timestamps, verifies semantic counts
inside the new generation, then atomically activates via a marker file.
Inactive generations are discarded; legacy files are never written. The
separate `schema_versions` registry table (one row per service) exists
because `PRAGMA user_version` is per-file and N services clobbered each
other, forcing full paragraph re-indexes every launch. **All of this is
load-bearing for any user upgrading from the pre-Solid-2 apps; none of it
should be removed until a deprecation decision is made.** The wiki layer
does not touch it: topics ship as a replaceable corpus outside the mutation
journal, like bible/writings.

## 9. Effect v4 idioms

`effect-solutions` CLI is not installed in this environment (`command not
found`); the scan below is from the effect/architecture skill checklists.

- No v3-era idioms found: no `Data.TaggedError`, no bare `Context.Tag(`
  service definitions, no `async/await` in Effect-native core modules.
  Errors consistently use `Schema.TaggedErrorClass`; services use
  `Context.Service` + `Layer.effect`/`Layer.succeed` with `layerTest`/`Test`
  factories on the seams that need them.
- `Effect.runSync`/`runPromise` appear only at legitimate boundaries:
  `packages/app/src/cache/synced-cache.ts` (Solid↔Effect bridge) and host
  entries. One exception inside a module body:
  `packages/core/src/gemini/client.ts:51` uses `Effect.runSync` — in the
  deferred-deletion gemini module, so not fixed.
- `packages/core/src/topics/service.ts` and `bible-db` use
  `Schema.decodeUnknownSync` on row fields; failures become defects rather
  than typed errors. `bible-db` wraps the equivalent in
  `BibleDataIntegrityError`; topics does not. Acceptable for a read-only
  catalog; worth aligning if the wiki overlay reuses the pattern.
